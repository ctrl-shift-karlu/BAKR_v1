**Names (owner, 2026-11-20):** the project is "BAKR - DNSC Scholarship Matching and Monitoring System" (`config('bakr.system_name')`; `config('bakr.tagline')` = the same without "BAKR - ", used next to the BAKR logo/name). Guidance for Claude Code when working in this repository. Read this first; read `README.md` for the full system description and `docs/ROADMAP.md` for planned work.

## What this is

**BAKR** is a Laravel web app for **Davao del Norte State College (DNSC)** students. A student registers, fills in one **matching form** (personal, academic, family & finances, other scholarships, achievements, provider questions: only questions a scholarship rule reads, no essays), and **hybrid matching** runs against 14 scholarships (DNSC internal, CHED, DOST, LANDBANK, CHED CoScho, BFAR, private; the last three added 2026-11-18 with their own provider accounts `landbank` / `bfar` (CoScho moved into `ched` on 2026-11-19), placeholder logins `<key>@bakr.test` in `.env`). **Hybrid matching (owner, 2026-11-19):** the deterministic rule engine checks the published hard limits (stored at once as `rule_status`); then the **Gemini AI matcher** (`AiMatchService` → `GeminiMatcher`, one structured-JSON request per saved application, run in the background from the results page via `student.results.ai-match`) reviews the whole **de-identified** application (`MatchProfile`) against each scholarship's published requirements + that rule check. Shown `status` = the **stricter** of the two (`ScholarshipMatch::stricter`): the AI can lower a result, never pass a failed published limit. `ai_match_status` on the application: pending / done / failed (rule results stay, retry) / off (no `BAKR_GEMINI_KEY`). A provider edit re-queues (pending). The AI writes the per-match explanation, fit, strengths / concerns / missing and the overview; the old explainer is only the fallback.

Public site: Home, About (aggregate stats incl. all four match outcomes + "Scholarships students match most"; team = Karl Angelo T. Gabaes, Rochelle D. Abella, Marielle Joie Javier, photos `public/images/img/team/member-1..3.jpg`; star-rating feedback form `partials/about/feedback` → `about.feedback` → `contact_messages` topic feedback + `aspects`, summary from approved shared feedback only; owner 2026-11-21), Scholarships catalogue, Contact (saves + emails messages). **No public Finder** (removed 2026-11-19; `/scholarship-finder` redirects to `route('find')`): matching requires a student account.
Student portal: dashboard, matches/results, profile & answer history, matching form.
Provider portal (real auth): `/providerLogin` → `/provider/*` (Overview, Scholars + Add scholars, Messages, Disbursements, Requirements, My scholarships). **No Applicants** (owner, 2026-11-18): providers only monitor scholars they already have; students apply with the provider directly and there is no "share a match" any more. Data comes only from the user's `provider_key` via `ProviderScope`. Providers edit their scholarships **one section at a time** (owner, 2026-11-19: Overview, Qualifications, Benefits, Documents to apply, Application period, How to apply, and Maintaining documents each have their own Edit button `?edit=<section>`, own form and Save; the hidden `section` input limits the save to `ProviderScholarshipController::SECTION_FIELDS`, so editing one section never touches another; text + rule wording/thresholds); the public Scholarships page renders from the same table.
**No "Add scholarship" (owner, 2026-11-21):** providers do not create scholarships in the portal (an Add scholarship page was built and removed the same day). The 14 scholarships come only from `config/scholarships.php` (`bakr:sync-scholarship`), owned by config `slugs` in `config/providers.php`; the Qualifications editor never adds or removes rules. The My scholarships header link is **"Official website"** = `Scholarship::officialWebsite()` (its `official_url`, else the provider's `website`; http(s) only).
**One account per ADMINISTERING provider (owner, 2026-11-19):** a scholarship goes into the account of whoever runs it, never its own account: CoScho is in `ched` (its old `coscho` login and `PROVIDER_COSCHO_*` credentials were deleted on 2026-11-21; `coscho` stays only as the scholarship slug); LANDBANK and BFAR are their own providers.
**Scholar status (owner, 2026-11-19):** providers see only **Active / Inactive / Terminated**. `scholars.status` stores `active` | `inactive` | `terminated`. **Every provider** terminates / reinstates its own scholars. Providers WITHOUT the `requirements` feature (documents handed in person at the official DNSC scholarship office, `config('bakr.scholarship_office')`) set **Inactive by hand** (Mark inactive / Mark active on the scholar profile); for the others `inactive` can't be set by hand and **Inactive is derived** (`Scholar::standing()`, scopes `withStanding()` / `whereStanding()`): an active scholar with a requirement still `missing` / `needs_revision` after its `scholar_requirements.due_on` (= the scholarship's deadline for that semester; the date field suggests the semester end, `AcademicTerm::endDate()`). Only the scholarship's own provider terminates / reinstates (`provider.scholars.status`, red confirmation); never set status from the details form. Providers preview uploads (`provider.requirements.file?inline=1`, PDF/JPG/PNG, `provider/partials/file-preview`); Download stays.
**Maintaining documents (owner, 2026-11-19):** edited on My scholarships in their OWN form (`provider.scholarships.documents`, only with the `requirements` feature; `provider/partials/maintaining-docs` + `maintaining-doc-row`). Each item in `scholarships.renewal_requirements` is `{name, note, types, max_mb, required}` (`App\Support\MaintainingDocument`; old plain strings still read via `fromText()`); always use `$scholarship->maintainingDocuments()`, never the raw column. Checklist items copy the settings (`scholar_requirements.is_optional / accepted_types / max_kb / instructions`); uploads validate against the item's own types/size. `required = false` ("only if it applies") never makes a scholar Inactive or blocks a stipend.
**Counting documents (2026-11-19):** an "only if it applies" item counts (to-dos, badges, x/y approved, KPIs, analytics) only once the scholar has sent it: `ScholarRequirement::isOwed()` / query scope `->owed()` (qualified columns, safe with a `scholars` join). Use them for every requirement count. **Terminated** = no more uploads (403), no to-dos, and `releaseBlocker()` locks any prepared stipend until the provider reinstates.
**One shared dashboard, per-provider pages:** `config/providers.php` `features` lists the OPTIONAL pages (`disbursements`, `requirements`; `ProviderScope::OPTIONAL_FEATURES`). CHED/DOST/Cebuana/Grab/LANDBANK/BFAR have both; **DNSC has neither** (no menu item, routes 404 via `provider.feature` middleware, sections hidden, its scholars can't upload). Check with `$scope->has()` (provider side) or `$scholarship->offers()` (student side). Never make per-provider view copies.
**Scholar roster:** providers add their existing official scholars one by one or from Excel/CSV (`ProviderScholarRosterController`, `ScholarRoster`, `App\Support\Spreadsheet` = dependency-free .xlsx reader/writer). **Scholar campus (owner, 2026-11-19):** `scholars.campus` (official campus name, nullable for older rows) is required when adding a scholar and feeds the admin "Scholars per campus" chart. The form is **campus select → program select** (the programs that campus offers, like the student form; `provider/partials/campus-program`, JS in `bakr-provider.js`; the old browser `<datalist>` is gone). Server: `ScholarRoster::campusRule()` + `campusProgramError()` refuse a program the campus does not offer; `ProgramCatalog::byCampus()` / `canonicalCampus()` / `inferCampus()` (DB first, `config/dnsc_campuses.php` fallback). Excel/CSV has an optional **Campus** column (understands "Samal", "Main"…); left empty it is inferred only when exactly one campus offers the program, else the row is skipped. Always read it with `Scholar::campusLabel()` (stored campus, else the single campus offering their program, else null = "Campus not set"). Shown on the provider's scholar list/profile (editable), the scholar's own profile and scholarship page. Roster scholars have `user_id` null + `full_name`/`email`; always use `$scholar->displayName()` / `contactEmail()` / `initials()`, never `->user->name`. Duplicates (same scholarship + student no. or e-mail) are skipped; approving an applicant whose e-mail is on the roster attaches the account to that row.
**Scholar ID + personal details (owner, 2026-11-20):** every scholar has a **Scholar ID** (`scholars.scholar_code`), **typed freely** by the provider exactly as their office writes it: **no format** (the per-scholarship format and `scholarships.scholar_id_format` were removed the same day, migration `2026_11_20_000002`); stored trimmed with inner spaces collapsed (`Scholar::normalizeCode()`, max `Scholar::SCHOLAR_CODE_MAX` = 40), case kept, unique per scholarship ignoring capitals (`ScholarRoster::scholarCodeError()`). Required on Add, in files (column "Scholar ID") and on the profile. Scholars list: search box includes it + "Scholar ID starts with" filter (`?scholar_id=`, `none` = no ID yet). The provider also records **required** `birthdate`, `gender` (**Male / Female only**, `Scholar::GENDERS`; files accept M / F), `mobile` (stored `09XXXXXXXXX`, `ScholarRoster::normalizeMobile`) and `address` (`ScholarRoster::personalRules()`, shared form partial `provider/partials/personal-fields`); files must have the Mobile number, Address, Birthday and Gender columns. Older rows may still lack them ("Not recorded yet" on the profile). Shown read-only on the scholar's Profile. Never sent to the AI or shown to the admin.
**Provider's scholar profile (owner, 2026-11-20):** `provider/scholars/show` = identity summary (`sp-id`) + status card + cards two per row (`sp-grid`, one column under 1200px): School · Scholarship details, Personal · Contact, then Maintaining documents · Stipend history. Same pattern as My scholarships: each card is read-only with its own **Edit** (`?edit=school|scholarship|personal|contact`); the hidden `section` input limits the save to that card's fields (`ProviderScholarController::SECTIONS`; no/unknown section = 422; the Scholarship card exists only with grant types or Disbursements, else 404). Every field of a card is required except the stipend. Styles in `bakr-provider.css` (`sp-*`).
**Scholar correction requests → provider Messages (owner, 2026-11-20):** "Request a correction" on the scholar's Profile (`#corrections`, `scholar.profile.correction`) creates a `ScholarMessage` (table `scholar_messages`, topics = the profile cards) for the provider of the chosen scholarship (the scholar's own rows only); it is **never** a `ContactMessage` and the admin never sees it. Providers read them on **Messages** (`ProviderMessageController`, `provider.messages`, open badge `navCounts['messages']`, always via `ProviderScope::messages()` / `message()`): reply (saved, shown on the scholar's Profile, e-mailed by `ScholarMessageReply`, marks handled), mark handled / reopen, open the profile card to fix (`?edit=<topic>`). The scholar Help form to the BAKR team no longer offers "Scholarship info needs updating" (`ScholarPortalController::helpTopics()`).
The provider types only the scholar's own details (Scholar ID, full name, student number, e-mail, program from the searchable DNSC list `ProgramCatalog::names()` (programs table, else the names in the `program_in` rules), year level 1st–4th; all required) plus the **grant type** when a scholarship has more than one (`scholars.grant_type`, e.g. CMSP Full / Half, TES categories). Status (Active), `started_term` (current term) and `stipend_amount` are filled in by `ScholarRoster` from **`scholarships.grants`** (config `grants`: `{key, label, amount, per: semester|month}`, taken from the published benefits; empty when no fixed amount is published, e.g. DNSC, Cebuana "up to"). Never invent an amount: add one to `grants` only with its official source, then `bakr:sync-scholarship`.
**Adding a scholar creates their login** (`ScholarAccounts`, owner's decisions 2026-11-17/18): the required e-mail becomes a **scholar** account (`role = scholar`, separate from student/matching accounts; role/status server-side) with a random 12-char temporary password, `users.must_change_password = true`, e-mailed by `App\Mail\ScholarAccountCreated` after the DB commit (`scholars.credentials_sent_at`; null = failed → provider "Resend login details" = new password). An existing scholar e-mail is linked (notice); an existing **student** e-mail is **converted** to a scholar account (same password, `converted` notice e-mail; their matching answers stay but are not shown); a provider/staff e-mail is refused. They sign in at **`/scholarLogin`** (`ScholarAuthController`, real auth); `password.changed` (`EnsurePasswordChanged`, role-aware) keeps them on `/scholar/password` until changed, then → Overview. The password is never shown to the provider or stored readable. With **`MAIL_MAILER=log`** mail bodies (incl. the password) go to `storage/logs/laravel.log` and nothing is delivered: `ScholarAccounts::mailIsTestMode()` then leaves `credentials_sent_at` null ("Login not sent") and the Add page shows a test-mode warning. Local `.env` uses Gmail SMTP again since 2026-11-17 (docs/CONTACT-SETUP.md).
**Scholar portal (real; separate accounts since 2026-11-18):** **student and scholar accounts are separate roles.** `student` = matching (`/studentLogin`, `/student/*`, `student.layout`); `scholar` = monitoring (`/scholarLogin`, `/scholar/*` behind `role:scholar`, own `scholar.layout`). Each refuses the other's credentials and routes (403 page offers the right portal). Migration `2026_11_18_000001_move_scholars_to_scholar_accounts` moved existing scholar-holding student accounts to `scholar`. Pages (`App\Http\Controllers\Scholar\ScholarPortalController`): Overview (summary + actions needed), `/scholar/scholarship` (same layout as the provider's My scholarships: `ms-hero` header + collapsible `ms-fold` sections for info, benefits, maintaining documents, stipends; the scholar layout also loads `bakr-provider.css`), `/scholar/requirements` (prototype Documents view: tiles, accordion rows, upload `<dialog>` with drag-and-drop / progress via XHR JSON to `scholar.requirements.upload` (`ScholarRequirementController`), preview via `scholar.requirements.file?inline=1` (PDF/JPG/PNG only, nosniff); `public/js/bakr-scholar-requirements.js`, `<noscript>` fallback; each scholarship's OWN list per semester; DNSC-type providers: "submit directly"), collapsible **Explore** (`/scholar/scholarships` without match results, `/scholar/help`, About, Public site), **Account** after the prototype's views: `/scholar/profile` (identity summary + Personal / Contact / School / Scholarship cards, read-only, "Request a correction"; no Address card: not collected) and `/scholar/settings` (Edit password `<details class="sc-collapse">` → `scholar.password.change.update`; "E-mail me a reset link" → `scholar.settings.reset-link`; red Sign out card → `<dialog id="confirm-signout">` → `scholar.logout`). Help body shared via `partials/portal/help`. The reset-password routes are not guest-only (a signed-in user can follow the e-mailed link; reset signs them out, clears `must_change_password`, and sends them to their own login). The old static `scholarDashboardF` prototype was removed on 2026-11-19 (backup in `docs/changes/backups/cleanup-2026-11-19/`); `/scholarDashboardF` still redirects to `/scholar`.
**"Scholar since" + semester deadlines (owner, 2026-11-21):** every scholar has a valid `scholars.started_term`, picked on Add / import ("Scholar since", `AcademicTerm::startOptions()`, default current) and editable on the profile's Scholarship card (every provider). No checklist and no stipend for a semester before it (`Scholar::startedBy()` / scope `startedBy()`; compare semesters with `AcademicTerm::indexOf()`, never as text). Each scholarship has its OWN maintaining-documents deadline per semester (`scholarship_deadlines`, `ScholarshipDeadline`), set on Requirements › "Deadlines for {semester}" (`provider.requirements.deadline`): saving it opens that semester's checklist and e-mails the scholars (`RequirementChecklist::setDeadline`, `ScholarNotifier` kind `deadline`; again when the date changes). **No "Open / Update checklist" any more.** The checklist follows by itself: `syncScholar()` after add / import / reinstate / new "Scholar since"; `syncScholarship()` after a maintaining document is added (current and coming semesters only).
**Stipend release rule (owner, 2026-11-18):** a disbursement can be marked **Released** only when `Scholar::releaseBlocker($term)` is null: every maintaining requirement of that semester is **approved** (submitted/waiting is not enough; not-yet-opened checklist blocks; providers without the `requirements` feature or scholarships with no renewal list are not blocked). Enforced in `ProviderDisbursementController` (single → validation error, bulk → skipped + notice); the page shows "Locked: …" and disables Released. **No On hold, no status dropdown (owner, 2026-11-22):** a record is only `pending` ("Not yet released") or `released`; each row has one **Release** button (`provider.disbursements.release-one`, optional reference; Locked = disabled button, released = "Done", already released = notice, nothing changes) plus the bulk "Mark selected as released". There is no way back to pending. Migration `2026_11_22_000001` turned old `on_hold` rows into `pending`. **No Midyear** anywhere: `AcademicTerm` has only 1st (Aug–Dec) and 2nd (Jan–Jul) Semester.
Admin portal (real, 2026-11-18; kept deliberately simple — 2nd-year BSIT final project): `/adminLogin` (`AdminAuthController`; the one account comes from `ADMIN_EMAIL`/`ADMIN_PASSWORD` via `AdminAccountSeeder`) → `/admin/*` (`role:admin`, `Admin\AdminController`, `admin.layout` on the shared dash shell): **Overview** (totals, "needs attention", system status), **Analytics** (owner's layout, 2026-11-19): four headline numbers, then three **table (left) + chart (right)** pairs, all server-rendered SVG/CSS, no chart library: (1) Matching = students per result per scholarship + donut of eligible matches (top 5 + "Other", `--viz-cat-*` colours) + "Did you know?" trivia (most / least matched); (2) Scholars = Active / Inactive / Terminated as a stacked bar chart only (`admin/partials/bars`; its table was removed on request), shown side by side (`.an-duo`, from 1280px) with the sign-ups line chart, each card with its own compact filter buttons (`.dash-seg.is-compact`); filter links `?scholars=scholarship|campus` change both (the campus is `scholars.campus`; older rows fall back to the only campus offering their program, else "Campus not set"); (3) Student sign-ups = new student accounts per day / week / month / year (`?signups=`) as a line chart only (`admin/partials/line`; its table was removed on request). Pairs sit side by side from 1280px; analytics tables are fixed-layout and turn each row into a "label · value" block when their wrapper is under 30rem (container query, `data-label` on cells). Long tables / lists are collapsed to their first rows with a "Show all N" button (`data-peek="N"`, `public/js/bakr-admin-analytics.js`; no script = fully shown); analytics tables wrap to fit, never scroll sideways. Below: "Why students don't qualify" and the per-provider table (documents approved, stipends released + ₱). **Accounts** (Students / Scholars / Providers tabs, search, deactivate/reactivate = `users.status`, e-mail a reset link; never passwords, never matching answers; admins not manageable here), **Scholarships** (read-only health: call status, verified_on > 6 months = "Check again", renewal list, revisions), **Messages** (open/all, mark handled = `handled_at`, approve shared feedback = `approved_at`). `RoleMiddleware` signs out an account that was deactivated. `/adminDashboardF` redirects to `/admin`; the old admin prototype (`adminDashboardF` view, `bakr-admin-dashboard.{css,js}`) and the prototype login scripts (`bakr-admin-login.js`, `bakr-staff-login.js`, `bakr-scholar-login.js`) were removed (backups in `docs/changes/backups/prototypes-2026-11-18/`). The official admin account is in the local DB (seeded from `.env`). **There is no Officer role** (dropped 2026-11-17).

**Installable app (PWA, owner, 2026-11-20):** BAKR installs as an app for every role (no native app, no API). `public/manifest.json` (relative URLs, **opens on the homepage** `./`; owner 2026-11-20), `public/sw.js` (**never caches pages**: personal data; offline → `public/offline.html`; caches only `css/` `js/` `images/`; bump `VERSION` on changes), `partials/pwa-head` in all four layouts, "Install the BAKR app" button `partials/pwa-install` (portal side-foot + public footer; iOS shows Add to Home Screen steps), `/app` (`AppStartController`: signed in → own portal, guest → `auth/app-start`; no longer the start page). **App mode** (owner: smooth, no animation delay): `bakr-app-mode.js` (head, not deferred) sets `html.is-app` in the installed app only; `bakr-app-mode.css` turns off animations, transitions, blur, scroll-reveal, preloader and view transitions there (spinners keep moving); `bakr-core.js` treats it as reduced motion; `bakr-pwa.js` prefetches links on touch (Speculation Rules, never files/downloads). ## Stack

- PHP ^8.3 in composer.json, but the locked packages need **8.4.1+** (local: 8.5; XAMPP's bundled 8.2 fails), **Laravel 13.17**, PHPUnit 12, Laravel Pint
- DB: **MySQL `bakr`** via XAMPP in local `.env` (`.env.example` now matches: MySQL `bakr`, `APP_NAME=BAKR`, all `BAKR_*` keys). Tests use SQLite `:memory:`.
- Sessions, cache, queue: `database` driver
- Frontend: **plain Blade + static files in `public/css` and `public/js`**, Bootstrap 5.3.8 + Bootstrap Icons from jsDelivr CDN, Google Fonts (Poppins, Source Serif 4). Assets are linked with `asset('css/...')`.
- **No Node, Vite or Tailwind.** `package.json` / `vite.config.js` were removed on 2026-11-19 (nothing used them; `composer setup` no longer runs npm, `composer dev` = `php artisan serve`). Don't add `@vite` to views.

php artisan config:clear                           # after any .env change
vendor/bin/pint                                    # code style

### Matching rules (config/scholarships.php → RuleEvaluator)

Rule types: `eq`, `in`, `not_in`, `gte`, `lte`, `income_lte`, `contains_any`, `contains_none`, `maybe_in`, `program_in`, `any_of`, `confirm`. `program_in` (DOST-SEI) compares the exact DNSC `program_name` with `pass` / `maybe` / `not` lists of DNSC program names taken from the provider's official list; a program in none of them is a confirm, so when DNSC adds a program, sort it into those lists. Options: `required`, `weight`, `skip_if`, `src` (page|web), `confirm_note`, `min_percent`.
**New questions vs. old forms:** a required tick-box group left out of an older saved form (e.g. `farm_fisher_family`, Part IV, added 2026-11-18 for LANDBANK / CoScho / BFAR: `rsbsa`, `coconut`, `fishr`, `none`) is dropped by `AnswerSanitizer`, so the fact is null and `contains_*` gives **unknown** (needs info), never a false fail.
**Rule semantics (2026-11-19):** only a **required** `confirm` holds a result at "nearly eligible"; an optional confirm is just a note. A rule with `'bonus' => true` (ranking points) never changes the status. A `program_in` list with `'open_list' => true` (CHED priority programs: `$chedPriority`, CMSP + BPMSP) never fails an unlisted program: it confirms with its own `confirm_note`. `top_five = unsure` is "needs info". Extra facts: `age` (from the birth date), `lives_in_davao_del_norte`, `shs_country`, `shs_strand`.
**Wording (owner, 2026-11-21):** the student's form is the **matching form**, never "application form" (that term is kept only for providers' official forms, e.g. "TDP Application Form"); routes, classes and tables keep their names (`student.application.*`, `ScholarshipApplication`).
**Household income brackets** (`ApplicationSchema::INCOME`, only 5: "Below ₱300k" (key `up_to_300k`, 0–300,000) · ₱300,001–350,000 · ₱350,001–500,000 · ₱500,001–2,000,000 · over ₱2,000,000) have their edges exactly on the published caps (₱300,000 LANDBANK/CoScho, ₱350,000 Cebuana, ₱500,000 CMSP, ₱2,000,000 BPMSP; BPMSP's finer income steps only change its ranking points).
**Which questions are asked (2026-11-19):** `'when'` on a field in `ApplicationSchema` + `ApplicationSchema::applies()`, shared by the form (`student-form.js`, `data-when`), the validator (`required_if`) and `AnswerSanitizer` (drops answers that do not apply): `first_year` = Grade 12 grade, Philippine SHS, SHS conduct (incoming AND current 1st-years: CMSP / GrabScholar read them); `incoming` = strand, Top 5, DOST exam; `upper` (2nd year and up) = college GWA + "within the normal length". A 2nd-year student is never asked about senior high school. A first-year counts as within the normal length (normalizer).
**Every question is answered (owner, 2026-11-21):** every tick-box group is `required` with `'none' => 'None of these'` + `'exclusive' => 'none'`; `has_awards` uses `'when' => 'talent'` (only after a real skill; checked in `ScholarshipApplicationRequest`). New questions must be required too. **"i" notes:** a field's `'info'` text (short, accurate, only what this project's rules check) renders an `.sp-info` button + `.sp-tip` note (`student/partials/field`, `student-form.js`); only for questions a student may not understand.
**Privacy Policy (owner, 2026-11-21):** `/privacy` (`route('privacy')`, `config('bakr.privacy_updated')`), Data Privacy Act of 2012 (RA 10173). Students agree at the end of the matching form on EVERY submit (`privacy_consent` always `accepted`). Linked from the footer, every sign-in page, register, the About-BAKR block (all portals), Contact and Help. When a feature changes what data BAKR collects, shows or sends, update the policy text and the date.
**Reminders vs eligibility:** the AI's `ai_notes.reminders` (documents, deadlines, slots) are shown as a "Reminders" note and never change a status; only `strengths` / `concerns` are findings. Old reviews stored them as `missing` (still read).
**Campus → program:** the form lists only the chosen campus' programs, and the request refuses a program that campus does not offer. The data is `config/dnsc_campuses.php` (DNSC's official per-campus list since 2026-11-19); `DnscCatalogSeeder` also removes programs a campus no longer lists. When a rule gets a new income cap, add a bracket edge for it (`IncomeBracketTest` fails otherwise). Old keys live in `LEGACY_INCOME` (readable, not offered).
Per-rule result: pass | fail | unknown | confirm | na. Status: any required fail → `not_eligible`; required unknown → `needs_info`; confirm or soft fail → `possible`; else `eligible`. Score = weighted (pass 1, confirm/unknown 0.5).
After editing a scholarship in config: use `php artisan bakr:sync-scholarship <slug>` (preview, then `--apply` after a DB backup). Do NOT re-run `ScholarshipSeeder` on the real DB: it overwrites every scholarship, including provider edits. Official sources live in `docs/sources/<provider>/<document>/` (page screenshots + `NOTES.md`); read `NOTES.md` before changing a scholarship. Provider edits in the portal go through `ScholarshipEditor`, which calls `ScholarshipApplicationService::rematch()` for every current application.

## Non-negotiable rules (privacy & safety)

1. **Hybrid matching: the AI may only make a result stricter (owner, 2026-11-19).** Published hard limits come from `RuleEvaluator`; the Gemini matcher's verdict is merged with `ScholarshipMatch::stricter()`. Never let AI output pass a failed rule, never trust an unvalidated reply (`MatchPrompt::parse`), never put AI text into HTML unescaped.
2. **De-identified AI input only.** Everything sent to an AI goes through `MatchProfile` (or `ExplanationPrompt`): never name, e-mail, mobile, street address / barangay, exact birth date or account ids; fields marked `'ai' => false` in `ApplicationSchema` are skipped; free text is scrubbed (e-mails, phone numbers, links, the student's name). Prompts treat student text as data (injection guard). Log only status codes on AI failure, never prompts.
3. **Data minimisation (PH Data Privacy Act 2012).** The matching form (owner, 2026-11-19) asks ONLY what a scholarship rule reads: no essays, sex, civil status, contact number, street address, parents' jobs or household size (removed the same day as unnecessary). Before adding a question, name the rule that reads it (`ApplicationSchema` header); mark it `'ai' => false` if the AI must not see it (the exact birth date). Consent type `data_privacy_ai` covers sending the de-identified form to Gemini.
4. **Always scope student data to `$request->user()->id`.** Never read an application/match ID from the URL without an ownership `whereHas`.
5. **Role and status are set server-side**, never from request input.
6. **Never invent thresholds.** If a provider doesn't publish a number, use a `confirm` rule.
7. **Public stats are aggregates only**, groups < `MIN_GROUP_SIZE` (10) hidden.
8. **Never change `APP_KEY`** on an existing DB — encrypted answers become unreadable.
9. Never commit `.env`, `BAKR_GEMINI_KEY` or `BAKR_AI_KEY`.
10. **Only `public/` is web-facing (2026-11-22).** The project sits in XAMPP's `htdocs`, so the root `.htaccess` refuses everything outside `public/` (`.env`, `storage/`, `vendor/`). Never delete it or put files meant for the web outside `public/`. Every web response gets `SecurityHeaders` (frame / sniff / referrer / permissions); a password change or reset and an admin deactivation end the account's other sessions (`User::endSessions()`).
